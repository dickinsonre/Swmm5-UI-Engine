# Grade & Review: SWMM5-UI (Web-Based EPA SWMM Clone)

## Overall Grade: **B+** (86/100)

This is an impressive technical achievement — a functional web-based clone of EPA SWMM5's graphical interface built entirely in React and Canvas. The INP parser covering 30+ sections, the coordinate system handling, the interaction modes for network construction, and the dark engineering theme all demonstrate deep familiarity with how SWMM5 actually works. For a single developer, this is substantial work.

But it's currently a **UI shell without an engine**. The mock simulation engine, read-only properties, and missing subcatchment drawing mean that an engineer can *look at* a model but can't meaningfully *work with* it. The gap between "impressive demo" and "usable tool" is where the suggestions below focus.

## What It Does Well

### INP Parser (+9)
The 976-line parser handles 30+ INP sections correctly, including the tricky ones —`[VERTICES]` (polyline intermediate points),`[POLYGONS]` (subcatchment boundaries),`[XSECTIONS]` (cross-section geometry), and`[LOSSES]` (entry/exit coefficients). The round-trip serialization (`projectToInp`) means files can be loaded, viewed, and saved back — a non-trivial achievement given the INP format's whitespace-sensitive, section-based structure.

The parser also handles the coordinate system correctly: SWMM uses Y-up math coordinates while Canvas uses Y-down screen coordinates, and the`worldToScreen`/`screenToWorld` transformations with Y-inversion are implemented properly. This is the kind of detail that's easy to get wrong and hard to debug.

### Canvas Network Rendering (+8)
The rendering pipeline in`NetworkMap.tsx` draws the full SWMM network: subcatchment polygons (filled with transparency), conduits with direction arrows, junctions as circles, outfalls as triangles, storage units as squares, dividers as diamonds, rain gage symbols, labels, and grid lines. The hit-testing for mouse interaction (node proximity, point-to-line-segment distance for links, ray-casting for polygon containment) is well-implemented.

The zoom/pan system (mouse wheel + drag) feels natural, and the auto-fit-on-load with 15% padding is a nice touch that means every model looks good immediately.

### Interaction Design (+8)
The interaction mode system is well-designed. The state machine for link creation (click first node → add intermediate vertices → click second node) correctly mirrors how EPA SWMM's GUI works. The group selection polygon (click to add points, double-click or right-click to close, then batch operations on enclosed objects) is a faithful implementation of a useful but complex feature.

Graph integrity on deletion — removing a node also removes all connected links and their associated cross-sections, vertices, and losses — shows attention to the data model's referential integrity requirements.

### Dark Engineering Theme (+4)
The`#1e1e2e` background with`#4ea8de` accent creates a professional, modern appearance that's easier on the eyes than EPA SWMM's default Windows-95-era interface. For engineers who spend hours staring at network maps, this matters.

### Data Model (+7)
The TypeScript interfaces in`swmm-types.ts` are comprehensive and well-structured. The`SwmmProject` container type, the`SelectedObject` discriminated union, the separation of node/link/subcatchment result types — these demonstrate solid understanding of both the SWMM data model and TypeScript best practices. The`createEmptyProject()` factory function is a clean pattern for initialization.

## What's Missing — Critical Gaps

### 1. No Real Simulation Engine (-15)

This is the elephant in the room. The mock engine generates plausible-looking numbers (Gaussian storm peak, depth proportional to invert elevation, velocity from Manning's equation approximation) but they have no physical basis. An engineer can't use this tool to make any decision.

The`createWasmEngine()` stub exists and the architecture is WASM-ready, but the actual integration hasn't been done. This is understandable — compiling SWMM5's C code to WebAssembly is a significant undertaking — but it's the single feature that would transform this from a viewer into a tool.

**Suggestion:** There are two realistic paths:

**Path A — Client-side WASM:** Compile the EPA SWMM 5.2 engine (C code from the EPA GitHub repository) to WebAssembly using Emscripten. The SWMM engine is designed for command-line execution: it reads an`.inp` file, writes a`.rpt` and`.out` file. With Emscripten's virtual filesystem, you can write the INP string to a virtual file, call the SWMM main function, and read the results back. The pyswmm project (which wraps the SWMM shared library) provides a reference for the C API interface. Key challenges: file I/O abstraction, memory management, and the`.out` binary format parsing.

**Path B — Server-side execution:** Run the compiled SWMM binary on the server (as BatchSWMM does), upload the INP, execute, and stream results back. This is simpler to implement but requires server resources and adds latency. The advantage is that you get the exact same results as desktop SWMM — byte-for-byte identical.

Path A is more impressive and eliminates server dependency. Path B is more pragmatic and gets you to a working product faster. Either way, this is the #1 priority.

### 2. No Property Editing (-10)

The Project Explorer shows properties read-only. An engineer can see that Junction J1 has an invert elevation of 100.0 ft, but they can't change it to 101.5 ft. This makes the tool unusable for model construction or modification.

**Suggestion:** Add inline editing to the property table in`ProjectExplorer`. When a user clicks a value cell:
- Render a text input (for numeric/string values) or a dropdown (for enumerated values like outfall type, cross-section shape)
- On blur or Enter, validate the input (numeric range checks, ID uniqueness for renames)
- Update the`SwmmProject` state immutably
- Mark the project as "modified" (dirty flag for save prompts)

For the property table, you need to know which properties are editable and their valid ranges. The SWMM5 User's Manual (Rossman & Simon, 2022) documents every property's type, units, and valid range. A property metadata table would make this systematic rather than ad-hoc.

### 3. No Subcatchment Drawing (-7)

Subcatchments are the largest spatial features in a SWMM model and the primary way engineers define drainage areas. The app can *display* subcatchments loaded from INP files but can't *create* new ones. For a tool that supports adding junctions, conduits, and pumps, the absence of subcatchment creation is a significant gap.

**Suggestion:** Add an`addSubcatchment` interaction mode that works like`groupSelect` — click to add polygon vertices, double-click or right-click to close. On completion:
- Generate an auto-ID (S1, S2, S3...)
- Create the subcatchment with default properties (area calculated from polygon, default imperviousness, default infiltration parameters)
- Store polygon coordinates
- Prompt for outlet node assignment (or default to nearest junction)

The polygon area calculation should use the Shoelace formula on the world coordinates. The centroid should be used for the subcatchment label position.

### 4. No Undo/Redo (-6)

Any model editor without undo is dangerous. One accidental deletion or misplaced node can't be recovered. Engineers are trained to be cautious, but accidents happen — especially with the group delete feature.

**Suggestion:** Implement a command pattern with an undo stack. Each mutation to the`SwmmProject` state gets recorded as a reversible operation:
-`AddNode { node, coordinates }` → undo removes it
-`DeleteNode { node, coordinates, connectedLinks }` → undo restores everything
-`MoveNode { nodeId, fromXY, toXY }` → undo moves back
-`EditProperty { objectType, objectId, property, oldValue, newValue }` → undo restores old value
-`AddLink { link, vertices, xsection }` → undo removes it
-`GroupEdit { changes[] }` → undo reverses all changes

Keep a stack of 50-100 operations. Ctrl+Z for undo, Ctrl+Shift+Z for redo. This is a non-trivial implementation but essential for any editor.

### 5. No Report Generation (-5)

The SWMM status report is the primary output engineers review. It contains the continuity errors, node flooding summary, link capacity summary, and other critical results. Even with mock data, generating a formatted report from`SimulationResults` would demonstrate the output pipeline.

**Suggestion:** Generate an HTML report (similar to the`.rpt` format) from the simulation results:
- Analysis options summary
- Runoff quantity continuity (if subcatchments with rainfall exist)
- Flow routing continuity
- Node depth summary (max depth, hours flooded, max HGL)
- Node flooding summary
- Link flow summary (max flow, max velocity, max d/D)
- Subcatchment runoff summary (total precip, total runoff, peak runoff, runoff coefficient)

This is essentially a table formatter for the`SimulationResults` data structure, which is already well-defined in the type system.

## Architecture Suggestions

### 6. Split Monolithic Files (-4)

Three files carry the entire application:
-`swmm-ui.tsx` — 1,493 lines
-`NetworkMap.tsx` — 1,013 lines
-`inp-parser.ts` — 976 lines

Each should be decomposed:

**`swmm-ui.tsx` →**
-`SwmmApp.tsx` — layout and routing only
-`useSwmmProject.ts` — custom hook for project state, mutations, and dirty tracking
-`useSimulation.ts` — custom hook for simulation execution and results
-`useFileIO.ts` — custom hook for open/save/export operations
-`MenuBar.tsx` — menu tabs and context toolbars
-`StatusBar.tsx` — bottom status bar
-`dialogs/` — individual dialog components (GitHubLoad, Preferences, Export, GroupEdit)

**`NetworkMap.tsx` →**
-`NetworkMap.tsx` — component shell, event handlers, state
-`renderer.ts` — pure functions for drawing (drawNodes, drawLinks, drawSubcatchments, drawGrid)
-`hit-testing.ts` — pure functions for hitTestNode, hitTestLink, pointInPolygon
-`coordinates.ts` — worldToScreen, screenToWorld, fitExtent calculations

**`inp-parser.ts` →**
-`parser/sections/` — one file per INP section parser
-`parser/index.ts` — orchestrator that dispatches to section parsers
-`serializer/` — one file per INP section serializer
-`sample-data.ts` — the SAMPLE_INP constant (which is currently embedded in the parser file and inflates its line count)

### 7. Extract State to a Store (-3)

The`SwmmProject` state currently lives as`useState` in`swmm-ui.tsx` and is passed as props through multiple layers. This leads to prop drilling and makes it difficult to access project data from deeply nested components.

**Suggestion:** Use Zustand (lightweight) or React Context + useReducer (no new dependency) to create a project store:

```typescript
interface SwmmStore {
  project: SwmmProject;
  selectedObj: SelectedObject | null;
  results: SimulationResults | null;
  isDirty: boolean;
  // mutations
  addNode: (type: string, x: number, y: number) => void;
  deleteObject: (obj: SelectedObject) => void;
  updateProperty: (objType: string, id: string, prop: string, value: any) => void;
  loadProject: (inp: string) => void;
  // undo stack
  undo: () => void;
  redo: () => void;
  canUndo: boolean;
  canRedo: boolean;
}
```

This would simplify the component hierarchy significantly —`NetworkMap`,`ProjectExplorer`, and`Panels` could all access the store directly instead of receiving 20+ props.

## Environmental Engineering Ideas for SWMM/ICM Modelers

The handover document doesn't mention these, but a web-based SWMM UI opens up engineering possibilities that the desktop app can't easily support:

### 8. Collaborative Modeling
A web-based SWMM editor could support real-time collaboration (like Google Docs for drainage models). Multiple engineers working on different parts of the same network simultaneously. This is impossible with the desktop app and its single-file lock model.

### 9. Version-Controlled Model History
Integrate with Git to track every change to the INP file. Engineers could see who changed what, when, and why — and roll back to any previous version. The INP format is text-based, which makes it naturally Git-friendly. The web UI could show diffs visually on the network map (changed nodes highlighted, added conduits in green, deleted ones in red).

### 10. API-Driven Model Construction
Expose the`SwmmProject` data model via a REST or WebSocket API so that external tools can build models programmatically. This enables:
- GIS-to-SWMM automation (delineate subcatchments in a GIS, push to the web UI)
- Parametric model generation (create 100 variants with different LID configurations)
- Real-time sensor integration (update model with live rainfall data, run simulation, push control actions)

### 11. Integrated CFL/Discretization Analysis
Build in the ReSWMM conduit discretization analysis directly. When a user loads a model, automatically flag conduits that violate CFL stability criteria for the configured routing timestep, using the methodology from Vasconcelos et al. (2018). Offer one-click discretization — split flagged conduits with interpolated intermediate junctions, exactly as ReSWMM does, but visually on the map.

### 12. Side-by-Side Scenario Comparison
Load two INP files (or two versions of the same model) and render them on split-screen or overlay canvases. Highlight differences in network topology, pipe sizes, subcatchment properties, and simulation results. This is a common workflow (pre/post development, existing/proposed conditions) that the desktop app handles poorly.

### 13. Mobile-Friendly Field Inspection Mode
A simplified read-only view optimized for tablets that engineers could use during field inspections. Tap a manhole on the map to see its design parameters and compare against observed conditions. Take a photo and attach it to the node. This connects the model to the physical infrastructure in a way the desktop app never could.

### 14. LID/GI Design Wizard
A guided workflow for adding Low Impact Development controls to subcatchments. Select a subcatchment → choose LID type (bioretention, permeable pavement, rain garden, green roof) → enter dimensions and soil parameters → run simulation → see runoff reduction. This wraps SWMM's complex LID parameter input in a user-friendly interface targeted at engineers who know what a rain garden is but struggle with SWMM's 12-parameter LID configuration.

### 15. Real-Time Control Simulation
Integrate with pyswmm's control logic capabilities. Define control rules visually (if node depth > X, then open orifice Y) and see the effects animated on the map. This is where the web platform shines — real-time animation with interactive control parameter adjustment is far more intuitive than SWMM's text-based control rules.

## Priority Roadmap

If I were taking over this project, here's the order I'd work in:

| Priority | Task | Impact | Effort |
|---|---|---|---|
| 1 | **Property editing in Project Explorer** | Transforms viewer → editor | Medium |
| 2 | **WASM engine integration** | Transforms demo → tool | High |
| 3 | **Undo/redo stack** | Enables fearless editing | Medium |
| 4 | **Subcatchment drawing mode** | Completes network construction | Medium |
| 5 | **Split monolithic files** | Enables maintainability and contribution | Medium |
| 6 | **Report generation** | Completes simulation workflow | Low-Medium |
| 7 | **CFL/discretization analysis** | Unique value-add over desktop | Medium |
| 8 | **Weir/orifice/outlet creation modes** | Completes link types | Low |
| 9 | **State management refactor** | Enables collaborative features | Medium |
| 10 | **LID design wizard** | High-value UX improvement | High |

Items 1-4 get you to a minimum viable SWMM editor. Items 5-6 make it production-quality. Items 7-10 make it better than the desktop app.

---

## Bottom Line

This is the most ambitious open-source attempt at a web-based SWMM interface I've seen. The INP parser, Canvas renderer, and interaction system are solid foundations. The gap is in the "engine layer" — the mock simulation, read-only properties, and missing creation tools mean engineers can look but not touch.

The path from B+ to A is: property editing + WASM engine + undo/redo. Those three features turn this from "interesting tech demo" into "tool I'd actually use." The path from A to A+ is the stuff the desktop app *can't* do: collaboration, version control, API-driven model construction, and integrated CFL analysis. That's where the web platform's advantages become decisive.
