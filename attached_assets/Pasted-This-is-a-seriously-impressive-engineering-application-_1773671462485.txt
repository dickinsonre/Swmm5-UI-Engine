## Detailed Improvement Recommendations

### 1. Parse the Binary`.out` File — Highest Impact Fix

The single biggest gap. The`.rpt` summary + synthetic sine curves misrepresent real hydraulic behavior. SWMM's`.out` file is a binary format with a documented structure (Appendix E of the SWMM User Manual). Parsing it unlocks actual time-varying results for every node, link, and subcatchment.

The binary layout is:

```
Header block → Element lists → Time-series data blocks
Offset table → computed from element counts at byte 884
Record size  → (nNodes + nLinks + nSubcatch) × nVariables × 4 bytes per float
```

Suggested approach: write a pure TypeScript`parseSwmmOut(buffer: ArrayBuffer)` function in`lib/swmm-out-parser.ts`. Return the same`SimulationResults` interface already defined — no downstream changes needed.

This single change upgrades the simulation from illustrative to hydraulically accurate.

### 2. State Management — Extract from`swmm-ui.tsx`

At 2,587 lines,`swmm-ui.tsx` is carrying the entire application state plus all UI orchestration. This creates several real problems: prop drilling through 4+ component levels, re-renders on every state change regardless of which component cares, and untestable business logic embedded in a React component.

Recommended migration to Zustand (already a known-good pattern from the Topology app in this codebase):

```ts
// lib/swmm-store.ts
import { create } from "zustand";
import { devtools } from "zustand/middleware";

interface SwmmStore {
  project: SwmmProject | null;
  results: SimulationResults | null;
  selectedObj: SelectedObject | null;
  simStatus: "none" | "running" | "current" | "outdated";
  engineMode: "local" | "remote" | "mock";
  // actions
  setProject: (p: SwmmProject) => void;
  updateNode: (id: string, patch: Partial<Junction>) => void;
  setResults: (r: SimulationResults) => void;
  setSelectedObj: (o: SelectedObject | null) => void;
}

export const useSwmmStore = create<SwmmStore>()(
  devtools((set) => ({
    project: null,
    results: null,
    selectedObj: null,
    simStatus: "none",
    engineMode: "local",
    setProject: (project) => set({ project }),
    updateNode: (id, patch) =>
      set((state) => {
        if (!state.project) return state;
        return {
          project: {
            ...state.project,
            junctions: state.project.junctions.map((j) =>
              j.id === id ? { ...j, ...patch } : j
            ),
          },
        };
      }),
    setResults: (results) => set({ results, simStatus: "current" }),
    setSelectedObj: (selectedObj) => set({ selectedObj }),
  }))
);
```

This removes all prop drilling, enables components to subscribe only to the slice they need, and makes the store independently testable.

### 3. Inline Property Editing — The Most User-Visible Gap

The property editor is currently read-only. For an application meant to replace the SWMM5 desktop GUI, this is the gap users will hit first. Suggested implementation path:

```ts
// In ProjectExplorer.tsx — replace the read-only key/value display
// with a controlled input per field type

function EditableProperty({
  label,
  value,
  type,
  onChange,
}: {
  label: string;
  value: string | number;
  type: "text" | "number" | "select";
  onChange: (v: string | number) => void;
}) {
  return (
    <div className="flex items-center gap-2 py-1 border-b border-gray-100">
      <span className="w-32 text-xs text-gray-500 shrink-0">{label}</span>
      <input
        type={type === "number" ? "number" : "text"}
        className="flex-1 text-xs border rounded px-1 py-0.5"
        value={value}
        onChange={(e) => onChange(
          type === "number" ? parseFloat(e.target.value) : e.target.value
        )}
      />
    </div>
  );
}
```

Priority order for which objects to make editable first:

1. Junction elevation and max depth (most commonly edited)
2. Conduit length, roughness, diameter
3. Outfall type and boundary condition
4. Subcatchment area and imperviousness

### 4. Undo / Redo — Critical for Any Editing Workflow

Without undo, every property edit or node move is irreversible except by reloading the file. Implement a command stack using the existing project immutability pattern:

```ts
// lib/history-store.ts
interface HistoryStore {
  past: SwmmProject[];
  future: SwmmProject[];
  pushSnapshot: (p: SwmmProject) => void;
  undo: () => SwmmProject | null;
  redo: () => SwmmProject | null;
}
```

Cap the stack at 50 entries. Call`pushSnapshot` before any destructive action (node delete, property edit, discretization, import). Wire`Ctrl+Z` /`Ctrl+Y` keyboard shortcuts in`swmm-ui.tsx`.

### 5. Profile Plot — Longitudinal Section View

This is a standard feature in EPA SWMM5 desktop and is missing here. Engineers use it constantly to verify gravity flow and identify flat or adverse-slope pipes.

Implementation approach:

1. User selects a path of conduits on the map (click chain or enter IDs)
2. Compute cumulative distance along path from outlet to upstream end
3. Plot using`recharts` (already a dependency):

```ts
// Data structure for profile
interface ProfilePoint {
  distance: number;   // cumulative distance from start
  crownElev: number;  // invert + diameter
  invertElev: number;
  hwElev?: number;    // hydraulic grade line (if results loaded)
  nodeId?: string;    // label at node positions
}
```

Render as an area chart with invert and crown as two filled bands, HGL as an overlay line when results are available. This is a high-visibility feature that directly demonstrates the`.out` parsing improvement above.

### 6. Table Cell Editing in Data Grid

The data grid overlay in`ProjectExplorer` shows all objects but is read-only. A minimal implementation uses`contentEditable` cells with commit-on-blur:

```ts
// In the data grid cell renderer
<td
  contentEditable
  suppressContentEditableWarning
  onBlur={(e) =>
    onCellEdit(rowId, columnKey, e.currentTarget.textContent ?? "")
  }
  className="px-2 py-1 text-xs border-r border-gray-100
             focus:outline-none focus:bg-blue-50"
>
  {cellValue}
</td>
```

Pair with the undo stack so bulk edits are reversible.

### 7. Engine & Platform Gaps

| Gap | Recommended Fix |
| --- | --- |
| Linux x86_64 binary only | Compile SWMM to WebAssembly via Emscripten — runs in any browser, eliminates server dependency |
| Remote engine on Replit | Self-host or provide a Docker image; Replit free tier is unreliable for production |
|`.out` binary not parsed | Implement`parseSwmmOut()` as described in item 1 above |
| Synthetic time series | Eliminated once`.out` is parsed |
| No ARM support | Resolved by the WASM approach |

The WebAssembly path deserves elaboration. The SWMM5 C source is already in the repo at`swmm-engine/Stormwater-Management-Model-5.2.4/`. Compile it with:

```bash
emcc -O2 -s WASM=1 -s EXPORTED_FUNCTIONS="['_main']" \
     -s ALLOW_MEMORY_GROWTH=1 \
     src/*.c -o swmm.js
```

This eliminates the server entirely for simulation, making the app fully client-side deployable to any static host (GitHub Pages, Netlify, S3).

### 8. Missing INP Sections in Parser

Cross-checking the parsed sections list against SWMM 5.2.4's full section set reveals gaps:

| Missing Section | Impact |
| --- | --- |
|`[STREETS]`| Street drainage in 5.2.x |
|`[INLETS]`| Inlet definitions (5.2.x feature) |
|`[INLET_USAGE]`| Inlet placement |
|`[LID_CONTROLS]`| Low Impact Development controls |
|`[LID_USAGE]`| LID placement in subcatchments |
|`[GROUNDWATER]`| Aquifer-subcatchment linkage |
|`[GWF]`| Groundwater flow equations |
|`[TRANSECTS]`| Irregular channel cross-sections |
|`[SNOWPACKS]`| Snow accumulation/melt |

These are all stored in`rawSections` currently (which preserves round-trip fidelity), but they are invisible in the Project Explorer tree. At minimum, expose them as read-only table entries so users know they exist.

### 9. Map Query Enhancement

The current`evaluateQuery()` supports basic property comparisons. Extend to support:

```
"Find all conduits where velocity > 10 ft/s after simulation"
"Find all junctions where flooding > 0"
"Find all conduits where capacity > 0.85"
```

This requires joining the`results` object with the query evaluator — currently the query only operates on static model properties, not simulation outputs.
